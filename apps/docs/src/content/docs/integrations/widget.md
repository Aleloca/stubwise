title: Customer service widget
description: Embed a support chat backed by your project's documentation, with in-widget report creation, on any site.

The **customer service widget** is an embeddable chat you drop onto any website.
It answers your users' questions **only from your project's generated
documentation** — with citations — and, when it spots a bug or a piece of
feedback, it proposes a **report** the user can confirm, which lands in Stubwise
as a ticket.

A project can have **several widgets**, each with its own **name**, its own
**key**, and an **independent configuration** — exposed repositories, appearance,
language and daily caps. For example, a **"Webapp"** widget on your public site
and an **"Admin"** widget on your internal panel, each grounded on a **different
knowledge base**. Conversations and tickets carry the name of the widget they
came from.

It reuses the pieces you already have: the
[autogenerated docs](/docs/documentation/autogenerated/) power the answers, and a
**DSN** — same format as the [SDK](/docs/sdk/installation/) uses — identifies the
project and the widget.

## What it does

- **Grounded chat** — the widget retrieves the most relevant chunks from the
  **repositories you selected** for that widget and answers **only from that
  context**, listing the pages it used as textual **citations** (shown as
  `source: <page title>`, not clickable links). When the docs don't cover the
  question, it says so rather than inventing an answer.
- **Report creation** — when the conversation surfaces a bug or a suggestion,
  the widget **proposes a report**. The user reviews and edits it, and on confirm
  it becomes a ticket in Stubwise with **source `widget`**, the user's declared
  identity, the **name of the originating widget**, and the **chat transcript**
  attached.
- **Team visibility** — every conversation is readable by your team in the
  **Conversations** page of the project — transcript included, labelled with the
  widget it came from and **filterable per widget**.

## Requirements

Two things must be in place before the widget can do anything useful:

1. **Generated docs** — the chat answers from documentation, so at least one of
   the project's repositories must have its docs generated. See
   [Autogenerated documentation](/docs/documentation/autogenerated/).
2. **A widget** — in the project settings, open the **Widget** section and
   **create a widget** (a project can hold several). Give it a **name**, turn it
   **on**, and pick the **repositories** whose docs that widget's chat is allowed
   to draw from. In the same editor you set its **title**, **welcome message**,
   **accent color**, **language** (`it` / `en`) and, optionally, its **daily
   caps** (see [Operational notes](#operational-notes)); once saved, you copy the
   ready-made embed snippet carrying that widget's own key.

## Integration: script tag

The simplest way to embed the widget is a single `<script>` tag. The
**precompiled snippet** — with that widget's DSN already filled in — is shown in
the widget's editor once it's saved, ready to copy:

```html
<script src="https://YOUR_INSTANCE/widget.js" defer></script>
<script>
  window.addEventListener("stubwise:ready", () => {
    Stubwise.initWidget({
      dsn: "https://WIDGET_KEY@host/p/slug",
      user: {
        id: "user-123",        // required
        email: "jane@acme.com", // optional
        name: "Jane Doe",        // optional
      },
    });
  });
</script>
```

`widget.js` loads asynchronously and, once ready, publishes
`window.Stubwise` and fires the **`stubwise:ready`** event. Initialize the widget
inside that listener so `Stubwise.initWidget` is guaranteed to exist regardless of
load order.

:::note[Copy the snippet from the widget editor]
You don't have to assemble the snippet by hand: each widget's editor renders it
precompiled with that widget's key, host and slug already substituted — just
copy it. The snippet appears only after the widget has been saved (its key is
minted on creation).
:::

### The DSN

The `dsn` has the **same format as the SDK**, but it carries the **widget's own
key** — not the project's ingestion key:

```
https://WIDGET_KEY@host/p/slug
```

where `WIDGET_KEY` is the key of the specific widget (each widget has its own),
`host` is your instance's host and `slug` is the project's slug. The widget's
public API lives under `<host>/widget/<slug>/…`, and the key selects **which
widget** of the project serves the chat — its repositories, appearance, language
and caps. Like the SDK's ingestion key, the widget key is **publishable**: it
only allows that widget's public operations, never reading your tickets.

:::caution[Deleting a widget invalidates its key]
The widget key is revoked the moment the widget is deleted, so a snippet still
installed with that key **stops working** immediately. To rotate a key, delete
the widget and create a new one, then update the installed snippet.
:::

### The `user` parameter

`user` is the **identity the host site declares** for the current visitor:

| Field   | Required | Notes                                              |
| ------- | -------- | -------------------------------------------------- |
| `id`    | yes      | Your stable identifier for the user.               |
| `email` | no       | Attached to conversations and to reports.          |
| `name`  | no       | Display name.                                      |

This identity is carried through to the conversation and onto any ticket the
widget opens, so your team knows who they're talking to.

## Integration: npm

If you bundle your frontend, you can install the package instead of loading the
script:

```bash
npm install @stubwise/widget
# or: pnpm add @stubwise/widget / yarn add @stubwise/widget
```

```js
import { initWidget } from "@stubwise/widget";

initWidget({
  dsn: "https://WIDGET_KEY@host/p/slug",
  user: { id: "user-123", email: "jane@acme.com", name: "Jane Doe" },
});
```

Importing the package publishes `window.Stubwise` and fires `stubwise:ready` as a
side effect too, but with a bundler you can just call `initWidget` directly. Like
the SDK, `initWidget` is **built never to break the host app**: on any error — a
malformed DSN, a failed config fetch, the widget disabled — it mounts nothing and
at most logs a `console.warn`. A second `initWidget` call is a no-op, so you won't
get two widgets.

## Operational notes

:::caution[The declared identity is not verified]
The `user` you pass is **trusted as declared by the host site** — Stubwise does
not verify it. Treat conversations and reports as coming from *whoever the
embedding site says they are*. Embed the widget only on surfaces you control, and
don't rely on the widget's identity for anything security-sensitive.
:::

- **Daily caps per widget** — to bound cost and abuse, each widget has a daily
  cap on **chat messages** and on **reports** created through it, counted over
  that widget's own conversations. You set both from the widget's editor; leaving
  a field **empty** falls back to the **instance default** — **200 chat
  messages/day** and **50 reports/day**, tunable at deploy time via the
  `WIDGET_DAILY_MESSAGE_CAP` and `WIDGET_DAILY_TICKET_CAP` server environment
  variables.
- **Tickets from the widget** — reports arrive as tickets with **source
  `widget`**, carrying the user's declared identity, the **name of the widget**
  they came from, and a **transcript of the conversation** — the **last 10
  messages**, each truncated to 500 characters — so the team has the context that
  led to the report.
- **Conversations** — every widget conversation is stored and readable by the
  team in the project's **Conversations** page, transcript and citations
  included. Each conversation shows the **widget it came from** and the list can
  be **filtered per widget**.
- **Deleting a widget** — removing a widget **keeps its conversations**: they
  stay in the viewer, marked as coming from a **"deleted widget"**. Its key is
  invalidated at once, so any snippet still installed with that key stops working
  (see [the DSN](#the-dsn)). Existing tickets are untouched.
