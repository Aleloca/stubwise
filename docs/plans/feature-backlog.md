## 5. Programma centro nevralgico

- **Fase 0 — Fondamenta** ✅ (ruoli maintainer/operator, inbox azionabile per-utente con outbox e DM Slack con bottoni, run_ticket + /stubwise:run; design e piano in docs/plans/2026-08-31-phase0-foundations-*).
- **Fase 1 — Pianificazione interattiva (`ask_user`)** ✅ (l'agente che pianifica un fix può fermarsi con una domanda a scelta multipla — tool `ask_user` da un server MCP stdio bundlato nel worker —, il job si parcheggia in `awaiting_input` e riparte da solo alla risposta, data da inbox / DM Slack / pagina ticket dal richiedente o da un maintainer; kind di notifica `job.awaiting_input`, migrazione 0064, env `AGENT_QUESTION_MAX_ROUNDS` default 5; design e piano in docs/plans/2026-09-01-phase1-ask-user-*).
- **Fase 2 — Pulse proattivo** ✅ (Stubwise smette di aspettare che qualcuno apra la UI: un poller del worker rileva i progetti **fermi** — nessun job AI in volo o `held`, nessuna domanda aperta, nessuna PR aperta, nessun job di backlog o sessione di analisi in corso — e, nella finestra del mattino del fuso configurato, manda una notifica `project.pulse` con 2–3 proposte prese dal backlog di discovery, ordinate per urgenza/effort/analisi pronta; «Procedi» dall'inbox o dal DM Slack converte la voce in ticket e lancia il run, che si ferma sempre sull'approvazione del piano. Attivazione per progetto dal dettaglio in /team, subordinata al backlog di discovery, con cadenza in giorni; kind `project.pulse`, migrazione 0065, env `PULSE_POLL_MINUTES`/`PULSE_TIMEZONE`/`PULSE_SEND_HOUR`/`PULSE_WEEKDAYS_ONLY`, tool MCP `list_proposals`; design e piano in docs/plans/2026-09-01-phase2-pulse-*).
- **Fase 3 — Registro plugin/skill** ✅ (le skill e i plugin Claude Code dell'agente diventano configurazione d'istanza invece che una scelta hardcoded: un **registro** solo-admin da Impostazioni → Plugin tiene repo git pubblici https **pinnati a uno sha**, che il worker materializza in `/plugins/<slug>/<sha>/` sul volume `claude-plugins` — l'unico a montarlo — validando con `claude plugin validate --strict`, rifiutando gli alberi con symlink e chiudendo con uno **smoke run** che verifica che le skill compaiano davvero all'agente col namespace atteso. Abilitazione **per progetto** (Progetto → Plugin) per **sottrazione**, sulle singole skill e sui gruppi di hook: siccome il CLI non sa spegnere una skill di plugin, ogni run riceve una **copia filtrata** della dir più la deny rule `Skill(<plugin>:<skill>)`. Un plugin base `stubwise-base`, bundlato nell'immagine del worker e mai filtrato, inietta via hook `SessionStart` il **contratto della run** (worktree, branch, commit e PR li fa la pipeline; le domande passano da `ask_user`) e la skill `stubwise-conventions`. I plugin entrano nei run di fix (piano, ripresa, esecuzione, self-repair), nel deep dive e nella chat di analisi del backlog, con `--plugin-dir` + `--setting-sources ""` per un perimetro deterministico e senza mai caricare il `.mcp.json` del plugin; tutto il percorso è fail-open ma mai silenzioso. Coda `plugin_jobs` (kind `materialize`/`smoke`), migrazione 0066, env `PLUGIN_POLL_SECONDS`/`PLUGINS_DIR`, scenari **golden manuali** col CLI vero in `apps/worker/scripts/golden/`; design e piano in docs/plans/2026-09-01-phase3-plugin-registry-*).
