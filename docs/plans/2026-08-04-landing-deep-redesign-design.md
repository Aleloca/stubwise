# Landing docs: redesign profondo dei contenuti — Design

**Obiettivo.** La landing attuale (`apps/docs` → `/guide`) posiziona bene la
piattaforma ma resta superficiale: raggruppa più funzionalità per sezione e non
"fa vedere" il prodotto. Vogliamo portarla al livello di graphify.com: sezioni
dettagliate per pilastro, **pezzi di UI ricostruiti in HTML/CSS** con callout
annotati, una sezione trust con confronti espliciti, una FAQ. Il progetto è
open source: il dettaglio è un vantaggio competitivo, non un rischio.

## Principi

1. **Far vedere, non raccontare.** Ogni pilastro ha un mock di UI ricostruito
   (non screenshot: HTML/CSS nel tema della pagina — niente asset da tenere
   aggiornati, niente problemi di risoluzione/tema).
2. **Callout stile graphify**: etichette mono uppercase ancorate al mock che
   spiegano il dettaglio non ovvio (es. "ON PUSH — solo le pagine toccate dal
   diff vengono riscritte").
3. **Solo claim verificabili nel codice.** Niente "no telemetry" o numeri
   inventati: ogni affermazione deve corrispondere a comportamento reale
   (encrypted at rest, embeddings locali, fail-closed, ecc.).
4. **Identità invariata**: terminal/mono/ambra, dark-first con light completo,
   IBM Plex Mono, animazioni sobrie con `prefers-reduced-motion`.
5. **Inglese**, etichette UI citate testualmente dal catalogo i18n `en`.

## [02/09] DOCUMENT — "Docs that write themselves."

**Eyebrow**: `> document [02/09]` · ancora `#document`.

**Lead**:

> Connect a repository and the worker maps it into a Confluence-like Docs
> space: **technical** pages for engineers, **functional** pages for the team,
> **product** guides for your users. On every push only the pages whose source
> files changed are rewritten — and the push itself lands as a dated
> release-notes entry.

**Mock** (finestra app "stubwise · /docs/acme-api", layout a 2 colonne):

- *Sidebar albero*: `▾ acme-api` → Overview, **Payments service** (attiva),
  `▸ API`, `▸ Guides (product)`, poi `▾ RELEASES` con `Aug 4 · v1.4.2`,
  `Jul 29 · v1.4.1`.
- *Pagina*: titolo "Payments service", meta chip `technical` + "updated 2h ago
  · source: apps/server/src/payments", 2 righe di prosa realistica su
  `createCharge()` e webhook consumer.
- *Chat dock* (in basso nella pagina): domanda "Where are refunds handled?" e
  risposta con chip sorgente `payments.ts:88` + `Payments service`.

**Callout** (3):

- `ON PUSH` — Only pages whose source paths are in the diff get rewritten — the
  rest is left alone.
- `RELEASE NOTES` — Every push becomes a dated changelog entry in RELEASES.
- `GROUNDED CHAT` — RAG over docs and code, enriched by the knowledge graph.
  Embeddings are local (Ollama, bge-m3).

**Righe di dettaglio (kv)**:

- *Three classes* — Technical, functional and product pages, generated per
  surface with their own page budgets.
- *Secret verifier* — Public product pages pass a fail-closed audit before
  publishing — anything that looks like a secret is rewritten or excluded.
- *Nothing leaves* — pgvector + Ollama on your host: vector search and chat run
  entirely on the box.

**Link**: Autogenerated docs →, Code graph →.

## [03/09] PLAN — "From recurring feedback to a plan."

**Eyebrow**: `> plan [03/09]` · ancora `#plan`.

**Lead**:

> Feedback and feature requests skip the fix pipeline: an agent distills them
> into backlog items, embeddings keep the backlog deduplicated, and every item
> carries its own design document, estimates and refinement chat. When it's
> ready, it becomes a ticket — from the web UI or straight from Claude Code.

**Mock** (2 colonne + terminale full-width sotto):

- *Card voce di backlog* (sinistra): badge `Refining` `E3` `High urgency`
  `Medium risk`; titolo "Bulk CSV export"; meta "Requested 7 times · ≈ similar
  to “Excel export”"; 2 righe di design doc; box **AI suggestions**: "effort 3
  → 4 · Reason: export touches billing" con bottoni `Accept all` / `Dismiss`.
- *Chat di refinement* (destra): chip modalità `DOCS` / **`CODE — acme-api`**
  (attiva); messaggio utente "Where would the export hook in?"; stato agente
  *Investigating the code…*; risposta con riferimento a `orders/list.ts` e chip
  sorgente.
- *Terminale MCP* (sotto, `data-lang="claude code"`):

  ```
  > /stubwise:start
  ✓ item "Bulk CSV export" → ticket #218
  ✓ design + implementation plan attached
  ⚙ status → in_progress
  ```

**Callout** (3):

- `DEDUP` — ≥ 0.90 similarity merges into the existing item; the grey zone gets
  flagged "similar to".
- `CODE SESSIONS` — A read-only agent session investigates the repo and keeps
  its context across turns.
- `MCP` — @stubwise/mcp brings the backlog into Claude Code: attach designs and
  plans, convert, advance status.

**Righe kv**:

- *Every channel* — SDK feedback, widget, Slack, inbound webhook, manual
  tickets: they all funnel into the same intake; the origin ticket is closed
  automatically.
- *Deep dive* — On demand, the agent analyzes a repository on a read-only
  worktree and writes a technical-analysis section into the document.
- *Exit ready* — Convert to task, export as markdown, or keep refining.

**Link**: Backlog discovery →, Claude Code integration →.

## [04/09] FIX — "A fix that earns its merge."

**Eyebrow**: `> fix [04/09]` · ancora `#fix`.

**Lead**:

> Errors from the SDKs collapse into one ticket per fingerprint. The worker
> triages it, plans with a strong model in read-only mode, executes with a
> cheaper one in an ephemeral worktree, and runs **your** tests — the pull
> request opens only when they pass. You review, you merge.

**Mock**: timeline verticale "AI activity" di un ticket (stile della UI):

```
12:04  triage    bug · high · effort 2/5
12:06  plan      opus · read-only          [human gate: plan approved]
12:16  execute   sonnet · ephemeral worktree
12:31  tests     ✗ 1 failing → self-repair #1 (failure fed back)
12:39  tests     ✓ 41 passed
12:40  PR #87    fix: guard empty cart on checkout   ↗
13:02  merged    → ticket closed (webhook)
```

**Callout** (3):

- `TWO-PHASE` — A strong model plans, a cheap one executes. Usage is logged per
  model, per job.
- `SELF-REPAIR` — The worker runs your test command itself and feeds failures
  back to the agent, up to N retries.
- `IN CONTROL` — Gates by type and effort, plan approval, per-ticket and
  monthly budgets, held jobs.

**Righe kv**:

- *One ticket, not twelve* — Similar errors collapse by fingerprint before any
  AI runs.
- *Limit-aware* — At the provider's usage limit, running work pauses and
  resumes on its own.
- *PR review too* — Incoming pull requests can get an AI review with a verdict
  (off by default).

**Link**: How the pipeline works →, Automation & gates →.

## [05/09] WATCH — "Yesterday, already written up."

**Eyebrow**: `> watch [05/09]` · ancora `#watch`.

**Lead**:

> Every night the worker reads the day's commits and writes the standup: a
> description per commit from the actual diff, a summary per project, a rollup
> per developer. And a lightweight agent on your hosts pushes metrics, services
> and checks into the same place — with alerts on your webhook.

**Mock** (2 card affiancate):

- *Activity* ("activity · Aug 3"): header "acme-api · 34 commits · 3 authors"
  con badge ambra `3 new commits`; riassunto breve; 3 righe commit (sha chip +
  subject + autore), una espansa con la descrizione AI.
- *Monitor* ("monitor · vps-01"): barre CPU 38% / RAM 71% (con tacca di soglia)
  / disk 82% (ambra, oltre soglia); righe servizi `postgres ✓ · caddy ✓ ·
  worker ✓` (docker); check `https://api.example.com ✓ 200 · 84ms`; footer
  "last push 12s ago".

**Callout** (3):

- `FROM THE DIFF` — Descriptions read the change itself, not the commit
  message.
- `PUSH AGENT` — One container per host pushes data out. No inbound ports, no
  third-party service.
- `THRESHOLDS` — CPU, RAM, disk and check alerts land on your notification
  webhook.

**Righe kv**:

- *Incremental* — Regenerating a day reuses the descriptions of unchanged
  commits; only new ones get AI runs.
- *Identity-aware* — Commit authors resolve through the git identities linked
  in the team page.
- *Docker & PM2* — The agent discovers services on its own and reports their
  state.

**Link**: Daily activity reports →, Server monitoring →.

## [06/09] WHY SELF-HOSTED — "Your code never leaves your server."

**Eyebrow**: `> why self-hosted [06/09]`.

**Lead**:

> The tracker, the docs, the embeddings, the graphs, the reports: one compose
> stack on your host. The only things that go out are the ones you decide —
> pushes to your git provider, and the worker's calls to the AI provider with
> your credentials.

**Confronti ✗/✓** (3 coppie, layout a 2 colonne stile graphify):

1. ✗ A SaaS tracker keeps your stack traces — and your users' messages — in
   someone else's cloud. / ✓ Stubwise stores events, tickets, docs and reports
   in your Postgres, on your volumes.
2. ✗ Hosted "AI docs" tools ship your code to their embedding pipeline. / ✓
   Embeddings run on the box (Ollama, bge-m3): search and RAG never leave the
   host.
3. ✗ Per-seat pricing meters your team. / ✓ MIT license: your infra, your AI
   usage, nothing else to pay.

**Trust strip** (4 colonne):

- *Self-hosted* — Six containers, automatic HTTPS, backups = a couple of Docker
  volumes.
- *Your AI credentials* — API key or Claude subscription login; an ordered
  provider chain with failover.
- *Encrypted at rest* — Git credentials and per-project `.env` files are
  encrypted with your key.
- *Open source (MIT)* — You don't have to trust this page: read what the code
  does. [Read the source ↗]

**Link**: How we think about security → (`/docs/ai-pipeline/security/`).

## FAQ — "The questions we get first."

Accordion nativo (`<details>/<summary>`, niente JS). 6 domande:

1. **Is the AI mandatory?** — No. Without authenticating the `claude` CLI,
   Stubwise is a complete self-hosted issue tracker: ingestion, board,
   comments, milestones all work. AI jobs just stay queued.
2. **Which AI does it use?** — The worker drives the Claude Code CLI. You
   authenticate with an API key or a Claude subscription login, and can
   configure an ordered chain of credentials with failover. Models per phase
   are configurable (plan/execute).
3. **Does my code leave my server?** — Only where you point it: your git
   provider and your AI provider, with your credentials. Search, embeddings,
   docs and graphs are computed and stored on your host.
4. **What does it take to run?** — Docker Compose, one `.env`, six containers.
   Migrations apply themselves; the embedding model is a one-time
   `ollama pull`.
5. **Which git providers?** — GitHub and Bitbucket Cloud, behind a
   `GitProvider` interface designed to be extended (see CONTRIBUTING).
6. **How does it relate to Claude Code?** — Twice over: the worker *uses* the
   Claude Code CLI to do its jobs, and the `@stubwise/mcp` server lets Claude
   Code *drive* Stubwise — backlog, designs, plans and tickets — from your
   coding session.

## Note tecniche vincolanti

- **File**: componenti nuovi in `apps/docs/src/components/landing/`
  (`DeepDocs.astro`, `DeepPlan.astro`, `DeepFix.astro`, `DeepWatch.astro`,
  `Trust.astro`, `Faq.astro`); `Landing.astro` resta l'orchestratore.
- **Stili condivisi**: le primitive comuni (`.section`, `.term`, `.snippet`,
  `.t-*`, bottoni, `.callout`, `.kv`, `.rise`) migrano in `<style is:global>`
  annidato sotto `.sw-landing` (CSS nesting nativo), così i child component le
  riusano; ogni child tiene scoped solo il layout del proprio mock.
- **Callout**: posizionati absolute sul mock su desktop (inline style),
  impilati sotto il mock sotto i 60rem.
- **Reveal on scroll**: classe `.rise` + un IntersectionObserver unico nel
  wrapper; disattivato con `prefers-reduced-motion`.
- **Light theme**: i mock restano scuri (come i terminali attuali); il resto
  eredita i token light già definiti.
- **Link**: sempre `import.meta.env.BASE_URL` (mai `/docs/...` nei componenti).
- **Nessuna dipendenza nuova, nessun asset esterno.**
- Le ancore `#document/#plan/#fix/#watch` vengono linkate dagli indici dei
  pilastri in [01/09].
